# Claude Code

Prepares Claude Code to run from inside the sandbox. Be aware that without
`@net` claude can't reach Anthropic servers and must be added explicitly.

```sh
snug -p @claude -p @net DIR
```

## What the sandbox gets

| from the host | inside the sandbox |
|---|---|
| `~/.local/bin/claude` | (optional) read-only at `/snug/bin/claude` |
| `~/.local/share/claude` | read-only |
| `~/.claude/skills` | read-only |
| `~/.claude/plugins` | read-only and only plugins named in [`plugins`](#plugins) load |
| `~/.claude/.credentials.json` | a generated copy with the access token only |
| `~/.claude/settings.json` | a generated copy with display preferences only |
| `~/.claude.json` | not read from host; generated with onboarding done, auto-update off and the target trusted |
| `~/.claude/CLAUDE.md` | not read from host; a generated, read-only note telling Claude Code what this sandbox allows |

snug does not search `$PATH` for `claude`; it stages only
`~/.local/bin/claude`. For Claude Code installed elsewhere, see
[No `$PATH` lookup](filesystem.md#no-path-lookup).

Everything generated by `snug` lives in the sandbox's `$HOME`, which is a tmpfs. Changes
made inside never reach the host.

**What it does not get.** Your session history, the list of your projects,
other projects' transcripts, MCP servers configured on the host, and any
command from your settings: hooks, `apiKeyHelper`, `statusLine`, credential
helpers, `env`. Tool approvals you gave on the host are asked again.

## Credentials

The sandbox gets your **access token**, never the **refresh token**. A token
stolen from inside stops working when the access token expires, typically
within hours, instead of living for weeks.

Claude Code inside cannot renew the token, and snug warns before the run when
it has already expired. Run `claude` on the host to refresh it, or log in again
inside with `/login` (see [`login`](#login)). A login made inside is not saved
on the host; the next run starts from the host token again.

## `settings.json`

`~/.claude/settings.json` can name programs to run, so snug never binds it.
It reads the host's file as data and writes a new one with only these keys,
when the host has them: `model`, `theme`, `editorMode`, `verbose`,
`alwaysThinkingEnabled`, `autoCompactEnabled`, `includeCoAuthoredBy`,
`prefersReducedMotion`, `spinnerTipsEnabled`, `skipWorkflowUsageWarning`.
Every other key is dropped, including keys snug has never heard of.

- A value that does not look like a plain name (a `model` holding an ARN or a
  path, for example) is dropped and snug says so.
- The file is read as strict JSON, up to 1 MiB. Comments, a trailing comma or
  a larger file carry nothing, and snug says why.
- The sandbox can write the generated file; the write goes nowhere and the
  host's file is untouched. Anything written there lasts for the run, so it is
  not a boundary.
- `/etc/claude-code/managed-settings.json` is not visible inside, so an
  organisation's managed policy does not apply.

The same filter applies to the target's `.claude/settings.json` and
`.claude/settings.local.json`, see below. A target file that is a symlink or a
directory refuses the run.

## The target opens without the trust dialog

Claude Code normally asks "Quick safety check" before it opens a directory
you have never trusted. Inside snug it does not ask for the target, because
snug marks the target trusted in the sandbox's own `~/.claude.json`. The
host's file is not touched.

What would make that dangerous is removed from the target instead:

- `.claude/settings.json` and `.claude/settings.local.json` lose their
  `hooks` and every other command. Each is replaced, read-only, by a filtered
  copy.
- `.mcp.json` is replaced by one naming no servers, so a repository cannot
  start an MCP server.

This applies only to files that already exist. A file the sandbox creates
during the run is a real file in the target, and shows up in `git status`.

## `plugins`

Plugins installed on the host are visible but do not load, unless a profile
names them:

```toml
[profile.my-claude]
include = ["@claude", "@net"]
plugins = ["caveman", "code-review@claude-plugins-official"]
```

A name is bare or qualified by marketplace. A name that is not installed on
the host is an error. Every hook and script a named plugin ships runs inside,
with whatever the sandbox has: the writable target, the access token and, with
`@net`, the network.

## `login`

Inside the sandbox, `/login` prints a URL to open and asks for the code you
get back. That always works and needs nothing from snug.

`login = ["claude"]` lets `/login` open your browser instead:

```toml
[profile.claude-login]
include = ["@claude", "@net"]
login = ["claude"]
```

- `@net` is required; without it the run is refused.
- snug opens the page on the host with `xdg-open`, found on your `PATH`, and
  needs `DISPLAY` or `WAYLAND_DISPLAY` set. `xdg-open` would fall
  back to a text browser otherwise.
- Inside, `BROWSER` is `/snug/bin/snug-browser`, which hands the URL to snug.
  snug opens only Claude's own login page, for Claude Code's own client, at
  most five times per run and at most once every 30 seconds. Anything else is
  refused, and nothing opens:

  ```text
  $ $BROWSER https://example.com/
  snug: login bridge: refused an open request from the sandbox — not the Claude login URL snug pins (scheme, host or path): https://example.com/. Nothing was opened.
  ```

- The shim is a `/bin/sh` script, so the selection must have a shell inside
  (`@sys`); otherwise the run is refused. A profile that sets `BROWSER` in the
  same selection is a conflict.
- One login is pending at a time, at most three callbacks are relayed per run,
  and a login not finished within 10 minutes is dropped and its port released.
- The browser `xdg-open` starts is yours and may outlive the run.
- snug answers the browser's callback itself and passes the sandbox only the
  code and state, never a cookie.

**What you grant.** If you approve the login in your browser, the sandbox
gets a full login for the account you approved: an access token **and** a
refresh token, which it can copy out over `@net` and use for weeks (a refresh
token minted on the host lasted 26 days). Turn it on only for a sandbox you
would give your account to.

A login made inside is never written back to the host: snug cannot tell whose
account a token from the sandbox belongs to.

`login` is a list and joins across profiles as a set. `claude` is the only
value today.

## Other Claude Code sessions

With a credential and `@net`, the sandbox can reach your account's other
Claude Code sessions, including ones on machines snug does not sandbox. snug
cannot close that from this machine. The generated `settings.json` refuses
incoming peer messages and asks before reaching a peer on another machine,
but the sandbox can rewrite that file, so it is a default, not a boundary.
