# Git, ssh and GitHub identities

This is the chapter for the question "I have two GitHub accounts — how do I get
one of them into a sandbox?"

The short version, and the part that surprises people:

> **A sandbox gets exactly one identity, or none.** You write one profile per
> account and select one at a time. Selecting two is a hard error, on purpose.

## What an identity profile does

Selecting a profile with an `[identity]` block makes snug **generate** a private
git/ssh/gh configuration for the sandbox from the account you named. It does not
mount yours.

```toml
# ~/.config/snug/profiles.d/accounts.toml

[profile.gh-work]
description = "github: work account"
include = ["@net", "@git-ro"]
  [profile.gh-work.identity]
  gh_user   = "work-account"
  git_name  = "Your Name"
  git_email = "you@work.example"
  ssh_key   = "{home}/.ssh/id_work.pub"   # the PUBLIC half
  ssh_mode  = "agent-proxy"

[profile.gh-personal]
description = "github: personal account"
include = ["@net", "@git-ro"]
  [profile.gh-personal.identity]
  gh_user   = "personal-account"
  git_name  = "Your Name"
  git_email = "you@personal.example"
  ssh_key   = "{home}/.ssh/id_personal.pub"
  ssh_mode  = "agent-proxy"
```

Then:

```bash
snug -p gh-work ~/src/work-project          # the work account, and only it
snug -p gh-personal ~/src/side-project      # the personal one
```

`snug --dry-run -p gh-work ~/src/work-project` shows what that produced:

```text
PROFILES @sys @home @cwd-rw @parent-ro gh-work
  data   /home/you/.gitconfig                identity:gh-work+replaces:@git-ro
  data   /home/you/.ssh/config               identity:gh-work
  data   /home/you/.ssh/id_snug.pub          identity:gh-work
  data   /home/you/.ssh/known_hosts          identity:gh-work
  GIT_CONFIG_GLOBAL=/home/you/.gitconfig
```

Every one of those is `data` — **generated by snug**, not bound from your home
directory. `~/.ssh` itself is never mounted, so no private key enters the
sandbox, and the other keys in your agent cannot be enumerated or used.

Note `identity:gh-work+replaces:@git-ro`. `@git-ro` would have bound your host
`~/.gitconfig`; the generated one replaces it, because a pinned identity must not
sit alongside your host's credential helpers and `insteadOf` rules. `git` merges
its global config from *two* files, so snug also sets `GIT_CONFIG_GLOBAL`, which
replaces both outright.

## Why you cannot select two

```console
$ snug -p gh-work -p gh-personal ~/src/proj
snug: profiles "gh-personal" and "gh-work" pin different identities; select only one
```

This is a refusal, not a missing feature.

An identity profile hands the sandbox a **signing oracle** for one ssh key. It
can push to any repository that key can reach. If a sandbox held two, something
inside it would choose which one to push as — and "something inside it" is the
untrusted code you started snug to contain. There is no safe answer to "which
account did the agent just commit as", so snug refuses the question, naming both
profiles.

The same reasoning is why the error names both: you know what you selected, not
what it collided with.

## What "A + B" usually means, and how to do it

If you meant *"account A, plus some other capability"*, that composes fine —
identity is the only thing that conflicts:

```bash
snug -p gh-work -p @podman-build ~/src/work-project   # work account + containers
snug -p gh-work -p @tmp-shared ~/src/work-project     # work account + a shared /tmp
```

If you genuinely need both accounts, run **two sandboxes**. That is the honest
shape of the requirement: two identities means two boundaries.

## `ssh_mode`

| mode | what it does |
|---|---|
| `agent-proxy` | A filtering proxy to your already-unlocked host agent, exposing exactly the one pinned key. No key material inside, no passphrase prompt, other keys not enumerable. **This is the one to use.** |
| `host-agent` | Forwards the *entire* agent. Every key, usable and enumerable. Requires `--i-know`. |
| `none` | No ssh at all. |

`agent-proxy` requires `ssh_key`, and it must be the **public** half:

```console
$ snug -p gh-work ~/src/proj
snug: ssh_mode = "agent-proxy" needs ssh_key: the PUBLIC key file that pins
      which identity the sandbox may sign with
```

What pinning **cannot** do, stated plainly: it bounds *which* identity is
available, not *what gets signed with it*. Anything inside the sandbox can ask
the proxy to sign anything. That is inherent to every ssh agent forwarder, not a
gap snug will close later — so scope the key you pin to what you would accept the
sandbox doing with it.

## gh

Set `gh_user` and snug generates gh's `hosts.yml` in a private `GH_CONFIG_DIR`,
staged as a writable copy. Writable is deliberate: `gh` migrates and rewrites its
token file on first use, and a read-only one fails with "failed to write config
after migration". The copy is on a tmpfs, so the rewrite goes nowhere and your
host gh config is never touched.

Use `gh_host` for GitHub Enterprise.

## A note on where profiles live

`~/.config/snug/profiles.d/*.toml` — your own, no `@` prefix. snug never reads
configuration from beside the target directory, so a repository cannot ship a
profile that grants itself your identity. See [Profiles](profiles.md).
